# Translation workflow

> *Audience: maintainers adding a new translation or refreshing an
> existing one. Phase 1 supports French and German for one page;
> the workflow scales to any page or language.*

The NetSec website is published primarily in **English**, which is
the **authoritative** version. French and German translations exist
as a **beta** feature — visibly marked with a banner at the top of
the page that links back to the English source.

## Cost model

Zero recurring cost.

- The site does **not** call any translation API at runtime.
- Translations are static HTML files committed to the repository.
- Refreshing a translation is a manual edit, done with whichever free
  tool the maintainer prefers (Google Translate web UI, DeepL Free,
  asking a native-speaker MC member, or doing it themselves).
- The only automated piece is a drift detector that reports which
  translations have fallen behind their English source — no
  translation happens automatically.

## What is and isn't translated

| Class                                           | Translated? |
| ----------------------------------------------- | ----------- |
| Page chrome (nav labels, page titles)           | Yes         |
| Project-authored prose (the body of each page)  | Yes         |
| Privacy notice, accessibility statement         | Yes — but legal nuance: prefer review by a native speaker before publishing |
| Footer co-branding and EU funding statement     | Yes (the EU visual-identity manual provides official translations — use those verbatim) |
| Member bios and form submissions                | **No** — bios stay in whichever language the member submitted them |
| `data/bios.json` itself                          | **No** — single source of truth in English; role labels are translated at render time |
| Names, affiliations, dates, grant amounts       | **No** — unchanged across languages |

## File layout

For every translated page there are sibling files with the locale
suffix:

```
accessibility.html        # English (authoritative)
accessibility.fr.html     # French (beta)
accessibility.de.html     # German (beta)
```

A page is "translated" only if a sibling file exists; if it
doesn't, the language switcher chip on other pages still works but
falls back to the English version.

State is recorded in **`data/i18n-state.json`** — for every
(page, language) pair, the file lists the path to the translated
sibling and the SHA-1 of the English source at the moment the
translation was last refreshed. The drift checker uses this to find
stale translations.

## Adding a translation for a page

1. **Copy the English source** to a sibling with the locale suffix.
   For example, to add French for `grants.html`:
   ```bash
   cp grants.html grants.fr.html
   ```
2. **Set the locale and beta status** on the `<html>` element:
   ```html
   <html lang="fr" data-i18n-status="beta">
   ```
3. **Add the beta ribbon** right after `<body>`:
   ```html
   <div class="i18n-beta-ribbon" role="status">
     <span class="i18n-beta-ribbon-badge">Bêta</span>
     <span>Traduction automatique — la version anglaise fait foi.
       <a href="grants.html" hreflang="en">Voir en anglais →</a></span>
   </div>
   ```
4. **Translate the visible text.** Leave code blocks, version
   numbers, names, dates, and brand strings untouched. The
   `<link rel="alternate" hreflang="…">` head tags should appear on
   every variant.
5. **Update the language switcher in the nav** — set
   `aria-current="true"` on the chip for this language and remove it
   from the others.
6. **Register the file in `data/i18n-state.json`** under the page's
   `translations` map, with today's date and `status: "beta"`.
7. **Stamp the source hash:**
   ```bash
   python3 scripts/check-i18n-drift.py --mark-fresh grants.html fr
   ```
8. Open a PR. Native-speaker review is welcome before merge but not
   required for a beta translation.

## Refreshing a translation when English changes

1. Run the drift checker:
   ```bash
   python3 scripts/check-i18n-drift.py
   ```
2. For each stale entry it reports, open the English source and the
   translated sibling side-by-side. Port the changes across using
   any tool.
3. When done, re-stamp:
   ```bash
   python3 scripts/check-i18n-drift.py --mark-fresh accessibility.html fr
   ```
   This recomputes the SHA-1 and updates the date.
4. Commit both the translated HTML and the updated
   `data/i18n-state.json`.

## Reviewing a translation

Mark a translation as **reviewed** (drops the beta ribbon) by
setting both:

1. In `data/i18n-state.json`:
   ```json
   "status": "reviewed",
   "reviewed_by": "Marie Robin (FR)"
   ```
2. In the translated HTML:
   ```html
   <html lang="fr">   <!-- no more data-i18n-status attribute -->
   ```
   Remove the `<div class="i18n-beta-ribbon">` element.

Until both are done, the ribbon stays visible and search engines see
the page as a translation alternate of the authoritative English.

## Translated pages

As of Phase 2 (in progress):

| Page                  | EN  | FR  | DE  |
| --------------------- | --- | --- | --- |
| `accessibility.html`  | ✓   | beta | beta |
| `sitemap.html`        | ✓   | beta | beta |
| `privacy.html`        | ✓   | beta | beta |
| `index.html`          | ✓   | —   | —   |
| `people.html`         | ✓   | —   | —   |
| `grants.html`         | ✓   | —   | —   |

Pages with `—` use the language switcher chip as a no-op for that
language; clicking it currently 404s. The drift checker only
reports on registered translations, so missing pages don't pollute
the table.

## Phase 2 plumbing

- **Saved-preference redirect.** On every page load, if the user
  is on the authoritative English version of a page but
  `localStorage.netsec-lang` is `fr` or `de`, and an
  `<link rel="alternate" hreflang>` for that language is declared
  in the head, `assets/js/site.js` does a `location.replace()` to
  the matching variant. Never redirects the other way (FR/DE →
  EN), so the English fallback stays reachable if a translation
  is broken.
- **Self-rewriting language switcher.** Every page ships the same
  three-chip block (`EN / FR / DE` with `hreflang` attributes).
  `site.js` computes the per-page destinations from the current
  pathname so the markup is identical across pages.
- **`window.netsecT()`.** A small string-lookup helper exposed on
  `window` for the JS-rendered pages (`people.html`,
  `grants.html`) to translate role labels and other strings as
  they're injected into the DOM. The catalog lives at the top of
  `site.js` — extend it there when a new string needs translating.
  Strings of the form `"MC member · Switzerland"` translate only
  the prefix before ` · ` so country names stay in their
  original casing.

## Why not auto-translate via an API?

Two reasons.

1. **Cost.** Anything that runs every time the English file changes
   adds a recurring expense. Even the cheapest tier of DeepL / Claude
   / OpenAI translation API is a non-zero monthly bill for a project
   with no operating budget.
2. **Quality.** For a research-network site that publishes a
   GDPR-grade privacy notice and an accessibility statement that
   doubles as a legal claim, the right "translator" is a native
   speaker — usually an MC member. Machine translation is fine for
   the bootstrap and the beta phase; it shouldn't be the final word
   on a page that someone might rely on for their rights.

Manual translation, drift detection, and a beta ribbon together give
us a workable system at zero ongoing cost.
